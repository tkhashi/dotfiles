# ADR (Architecture Decision Records)

このディレクトリには、この Hammerspoon 設定における設計判断・バグ修正の意思決定記録を残す。

## 目的

- なぜその設計・修正を選んだのかを後から追えるようにする
- 同じ調査を繰り返さないようにする(特にバグ修正: 原因調査に時間がかかったものほど記録する価値が高い)
- 将来同種の問題が起きたときに、過去の判断とその根拠を参照できるようにする

## 記載タイミング

**バグ修正のADRは、ユーザーによる実機での動作確認が完了した後に記載する。**
修正直後・未検証の段階でADRを書くと、原因の推測が誤っていた場合に誤った記録が残ってしまうため。動作確認が取れるまでは会話内でのみ原因・修正内容を共有し、確認完了後に本ディレクトリへ記録する。

## 対象

- アーキテクチャ上の設計判断(例: なぜMediatorパターンを採用したか。これは `ARCHITECTURE.md` 側に記載)
- バグ修正のうち、原因調査や設計判断を伴うもの(単純なtypo修正等は対象外)
- 既存の挙動を変える判断(トレードオフがあるもの)

## ファイル命名

```
NNNN-短いタイトル.md
```

- `NNNN` は4桁の連番(0001, 0002, ...)。このディレクトリ内の既存ファイルの最大値+1を使う
- タイトルは小文字ケバブケース、英語 or ローマ字で簡潔に

## テンプレート

新規ADR作成時は以下の構成に従う。

```markdown
# NNNN. タイトル

- Status: Accepted
- Date: YYYY-MM-DD

## Context(背景・問題)

何が問題だったか。どういう状況で気づいたか。

## Decision(決定・原因)

原因(バグの場合)、または採用した設計判断。
関連するファイル・行番号を明記する。

## Consequences(結果・影響)

この決定によって何が変わるか。トレードオフ・残課題があれば書く。
```
